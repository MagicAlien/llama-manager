**This file grows and nothing trims it by itself.** It is read in full at the start of every session, so its length is a running cost paid out of the context budget you need for the work. Pruning is a correction task (`docs/WORKFLOW.md` §7) and is commissioned at the close of a milestone, never done in passing. The rules differ per section and the asymmetry is the point:

- **Done** — compress to one line per milestone plus the PR numbers once the milestone closes. The diffs already hold the detail, and better than prose does.
- **Observations** — triage each one: it becomes a `T-1xx`, or it is closed with the reason it no longer applies, or it stays. "It stays" must be a decision someone made, not what happens when nobody looks.
- **Discrepancies** — a `resolved` entry keeps its one-line summary and its resolution, and loses its working detail.
- **Facts established — never pruned.** Every line there cost an experiment to learn. Deleting one means a future session rediscovers it the expensive way, which is the exact failure this file exists to prevent. If the file must get shorter, it gets shorter somewhere else.

### D-012 — `AppError::RateLimited`'s field is a duration, but T-020's acceptance text says "reset time"
- Type: discrepancy (the field's semantics differ from the acceptance text's wording)
- Found in: T-020, pre-implementation review
- Evidence: `docs/TASKS.md` T-020's acceptance text reads "a rate-limit response returns `AppError::RateLimited` carrying the reset time." GitHub's own REST shape corroborates the split: a live capture of `GET /repos/ggml-org/llama.cpp/releases?per_page=1` (1 Sept 2026) returned `X-RateLimit-Reset: 1788289802` — a unix **timestamp** (~4994 s ahead of the capture's `now` `1788286848`) — and **no** `Retry-After` header on an un-throttled `200`. ### F-020 — The router's own report: `/models` states, the preload key, and the absence of a cooperative stop (T-040, build b10883)

Read off the installed b10883 build by starting it with a one-section preset (`--no-webui --host 127.0.0.1 --port 49777 --models-preset <file>`) and reading its endpoints directly; the status vocabulary was then cross-checked against the source at that build's own commit `91f6a6cf3` (`tools/server/server-models.h`), not from memory.

- **`/models` and `/v1/models` returned byte-identical payloads** (600 bytes each) on this build, so "distinguish `/models` from `/v1/models`" (T-041) has no textual difference to key on today — what differs is intent, not shape. An entry carries `id`, `aliases`, `tags`, `object`, `owned_by`, `created`, `status`, `architecture`, `source`, `can_remove`.
- **The load state lives in `status.value`**: `downloading | downloaded | unloaded | loading | loaded | sleeping`. A failure is **not** a state of its own — the model goes back to `unloaded` and the status object gains `"failed": true` **and** the child's `exit_code` (`server_model_meta::is_failed()` is `UNLOADED && exit_code != 0`). A reader that looks only at `value` sees a failed preload as an idle model; the flag is what makes it visible.
- **The preload key is `load-on-startup = 1`** — a *preset option* (`COMMON_ARG_PRESET_LOAD_ON_STARTUP`), never a CLI flag, so it can never appear in `verified_flags` and its warrant is the preset interface itself. Verified by behaviour rather than by acceptance: a section carrying it made the router log `(startup) loading model t040-probe` and spawn a child for it before answering any request.
- **The router spawns a child process per model**, and `/models` reports that child's own argument vector (with its OS-assigned port) in `status.args`. A real run showed a child PID under the router's PID. Killing the router alone can therefore leave children holding VRAM: the tree kill is not defensive, it is necessary.
- **Nothing stops this build politely.** `taskkill /PID <pid>` (no `/F`) is refused — *"Questo processo può essere terminato solo forzatamente"* — and `AttachConsole(pid)` + `GenerateConsoleCtrlEvent(CTRL_BREAK_EVENT, pid)` fails with `ERROR_ACCESS_DENIED` (5) against a child spawned with `CREATE_NO_WINDOW`/`CREATE_NEW_PROCESS_GROUP`, leaving the process alive. The shared grace window is therefore currently waited out in full before the tree kill.

### F-019 — Every VRAM term was measured against the pinned build's own accounting, and three of the documented model's rules are wrong (T-038, build b10883)

The measurement method, reusable: run the installed `llama-server.exe` **with the owner's real model and `-lv 5`**, and read its own buffers. `-c 512 -ngl 0 --no-warmup --load-mode mmap` loads in ~6 s on CPU (mmap, no weights read) and prints `llama_kv_cache: size = …` and `llama_memory_recurrent: size = …`. The same run also prints the model's whole geometry as llama.cpp sees it (`print_info: n_layer = 64, n_layer_all = 65, n_embd_head_k = 256, n_gqa = 6, ssm_d_state = 128`). Everything below was read off that output, not derived from the document.

- **Only the full-attention layers hold a KV cache.** `{arch}.full_attention_interval = 4` with `block_count = 65` → llama.cpp reports `16 layers` and marks the others `filtered` (`llama_kv_cache: layer N: filtered`, with `dev = CPU` on layers 3, 7, 11, … 63). Sizing the cache for all 65 layers overestimates this term **4.1×**, and it was the dominant cause of the owner's "the projection reads too large".
- **`attention.key_length` / `attention.value_length` are the per-head dimensions, not `embedding_length / attention_head_count`.** The real file declares 5120 with 24 query heads and 256-wide heads; the division yields 213. The build agrees with the declared value (`n_embd_head_k = 256`).
- **The KV cache is priced per head and byte-exact with the measured numbers**: `512 cells × 16 layers × 4 KV heads × (256×2 + 256×2) = 33 554 432 B = 32.00 MiB`, which is exactly what the build prints (K 16.00 + V 16.00).
- **`q8_0` KV is 8.5 bits per element (1.0625 bytes), not 8.** A `-ctk q8_0 -ctv f16` run reports `K (q8_0): 8.50 MiB` where a flat byte per element predicts 8.00. `q4_0` at 0.5625 bytes/element is confirmed the same way (`4.50 MiB`). The documented model's `1` for `q8_0` is 6 % low.
- **A hybrid model's recurrent state is a real, context-independent term.** Formula taken from llama.cpp's own `llama_hparams::n_embd_r()`/`n_embd_s()` at the build's commit (`91f6a6cf3`), and it reproduces the reported buffer to the byte: `n_embd_s = ssm.state_size × ssm.inner_size` = 786 432, `n_embd_r = (conv_kernel−1) × (inner_size + 2·group_count·state_size)` = 30 720, × 4 bytes (f32) × 48 recurrent layers → **149.62 MiB per sequence** (`R 5.62 + S 144.00`), and ×4 = 598.50 MiB for four. It **never grows with the context** — the build's number is identical at `-c 512` and at any other context.
- **The recurrent layers are `block_count − nextn_predict_layers − attention_layers`**: llama.cpp runs the model on `n_layer = n_layer_all − nextn_predict_layers` repeating layers (64 of 65 here), of which 16 are full-attention → 48.
- **The draft stage multiplies the recurrent state by `1 + --spec-draft-n-max`.** Measured: no drafting → `0 rs_seq` (×1); `--spec-type draft-mtp` → `3 rs_seq` (×4, the flag's own default 3); `--spec-draft-n-max 1` → `1 rs_seq` (×2); `--spec-draft-n-max 5` → `5 rs_seq` (×6). On this model four sequences cost **2394.00 MiB** of recurrent state, where one costs 598.50.
- **The MTP layers run in their own context with their own cache**: with `--spec-type draft-mtp` a second KV report appears — `2.00 MiB (512 cells, 1 layers)` — and 215 MiB of weights (`blk.64.*`) are loaded that a non-drafting launch reports as `unused tensor`.
- **A draft companion is a second model**: `--model-draft <dflash2>` reports its own `model buffer size = 1033.21 MiB` (the file is 1 094 346 016 B) and its own `llama_kv_cache: 10.00 MiB (512 cells, 5 layers)` — which is the same KV formula applied to its own header (5 layers, 8 KV heads, 128-wide heads).
- **The recurrent state is allocated per server slot, and the slot count is `--parallel`'s business** (`default: -1, -1 = auto`, which this build resolves to 4): the same model reports `149.62 MiB` at `--parallel 1` and `598.50 MiB` at the default. The *KV* cache is not affected (the unified pool is sized to `n_ctx`, not per slot).
- **The fixture files were wrong in the same way the reader was.** `google-gemma-Q4_K_M.gguf`, `microsoft-Phi-3-mini-Q4_K_M.gguf` and `mistralai-Mixtral-8x7B-Q8_0.gguf` carried `llama.`-prefixed keys under a `gemma`/`phi3`/`mixtral` architecture — files no real writer emits. They passed because the reader had the same fixed-prefix assumption: self-consistent wrongness, the class F-013 records for the wire-type codes. Regenerated in T-038; `scripts/make-gguf-fixture.py` now derives the header's KV count from the list of pairs it writes, so the count cannot drift from the content again.

### F-015 — The preset INI grammar: key spelling, section names, and what the router does with a key it does not know (T-036, build b10883)

Every line below was measured by starting the real `llama-server.exe` (b10883-cpu-dir, the installed active build) with a one-section preset and reading its own `--log-file` output — not inferred from the INI grammar or from `--help`.

- **A preset key is the flag's own name with its dashes preserved, minus the leading `--`**: `--ctx-size` → `ctx-size = 8000`; `--cache-type-k` → `cache-type-k = f16`. Underscore spellings (`ctx_size`, `cache_type_k`, `gpu_layers`, `flash_attn`, `n_cpu_moe`, `tensor_split`, `main_gpu`, `batch_size`, `ubatch_size`) are **not** recognised.
- **An unrecognised key is fatal for the whole server, not for that model**: startup ends with `E srv llama_server: failed to initialize router models: option '<key>' not recognized in preset '<section>'` and the process never listens. There is no "ignore unknown key" path, so a misspelled key cannot be discovered at model load — it kills the router before any request.
- **A key that the build does not have at all is equally fatal**, which is why emitting a flag requires checking it against the build's verified list. Concretely: b10883 has no `--no-mmap` and no `--mlock` (both retired into `--load-mode`), so `no-mmap = 1` and `mlock = 1` refuse to start the server; b9196 (the build `docs/verified-flags.md` was generated from) still had them.
- **The section name is the served name**: `[test-external]` appears in `/v1/models` as `id: "probe"` / `test-external` — there is no `served_name` key, and writing one refuses to start the server.
- **Short aliases work as keys too** (`ngl`, `c`, `fa`, `md`), so a build that drops a long name can still be driven through its alias.
- **Verified accepted as preset keys on b10883** (each tested individually): `gpu-layers`, `ctx-size`, `batch-size`, `ubatch-size`, `flash-attn`, `cache-type-k`, `cache-type-v`, `n-cpu-moe`, `main-gpu`, `threads`, `tensor-split`, `chat-template`, `spec-type`, `spec-draft-model`, `model-draft`, `spec-draft-n-max`, `spec-draft-n-min`, `spec-draft-p-min`, `spec-draft-p-split`, `spec-draft-ngl`, `spec-draft-type-k`, `spec-draft-type-v`, `spec-draft-threads`, `threads-draft`, `gpu-layers-draft`, `draft-p-min`, `spec-default`, `draft`, plus the aliases `ngl`, `c`, `fa`, `md`. Unknown-value validation happens later, at model load: `spec-type = bogus-value` is accepted at startup.
- **A `--spec-type` value validation does not happen at preset parse time**, so a preset that starts may still fail when the model is actually loaded. Startup acceptance proves the key grammar, not the semantics.
- **The `--spec-type` enum for this build** (from its own `--help`): `none, draft-simple, draft-eagle3, draft-mtp, draft-dflash, draft-dspark, ngram-simple, ngram-map-k, ngram-map-k4v, ngram-mod, ngram-cache`. This is the source of `core::speculative`'s draft-architecture → spec-type mapping. `--draft`, `--draft-n`, `--draft-max`, `--draft-min`, `--draft-n-min`, `--spec-ngram-size-n/m`, `--spec-ngram-min-hits` are documented in the help as **removed** (they parse as preset keys but their values are no-ops).

### F-017 — The two capability questions are answered by the file's own `tokenizer.chat_template`, not by the vocabulary (T-037)

Read out of the owner's real `Qwen3.8-27B-NVFP4-MTP-HIGH.gguf` in `%USERPROFILE%\.lmstudio\models\esatapedico\`, header-only, with a standalone KV dump cross-checked against F-013's wire codes. - **Thinking is declared by the template's own reasoning block**: the assistant turn opens with the delimiter pair `<think>` / `</think>`, **byte-verified from the real file** — the sequence around the token is `'\n<think>\n'` (character codes 0x27 0x5c 0x6e 0x3c 0x74 0x68 0x69 0x6e 0x6b 0x3e 0x5c 0x6e 0x27): the delimiter itself is plain <think>, and the \n beside it is the Jinja escape, **not part of the token**. ### F-005 — `cargo fmt --check` prints a diff and exits non-zero on any drift; there is no separate "clean" banner to look for (T-011)

Confirmed by the owner after this task's first CI failure looked contradictory: a local `cargo fmt --check` run had printed a diff listing (`Diff in <path>:<line>: ...`) but no loud top-level error, and was read as passing on that basis. It wasn't — `cargo fmt --check`'s *only* success signal is empty output and exit code 0; any printed diff, however it's formatted, means the command is about to fail (and does, with exit code 1, once every file has been checked). There is no intermediate "diff shown but still clean" state. Worth remembering for any future session or human reading local gate output by eye rather than checking `$LASTEXITCODE`/`$?` directly: if `cargo fmt --check` printed anything at all, it did not pass.

### F-006 — GitHub's rate-limit headers: `X-RateLimit-Reset` is a unix timestamp; `Retry-After` (a duration) appears only on a throttled response (T-020)

Confirmed by a live capture of `GET /repos/ggml-org/llama.cpp/releases?per_page=1` on 1 Sept 2026: the `200` response carried `X-RateLimit-Limit: 60`, `X-RateLimit-Remaining: 56`, `X-RateLimit-Used: 4`, `X-RateLimit-Resource: core`, `X-RateLimit-Reset: 1788289802` — a unix timestamp (≈4994 s ahead of the capture's `now`, `1788286848`), i.e. an absolute reset *time*, not a duration — and **no** `Retry-After` header. GitHub sends `Retry-After` (seconds, a duration) only when the response is itself a rate-limit error. This is why T-020's `RateLimited` handling prefers `Retry-After` when present, else derives `retry_after_seconds = X-RateLimit-Reset − now`, else falls back to a fixed default (see D-012 for why the acceptance text's "reset time" wording and the field's duration semantics differ).

### F-004 — Neither `driver_ok` nor `cuda13_ok`'s numeric floor is written down anywhere in this repo, but both are answerable from NVIDIA's own public documentation (T-010)

`docs/CONTRACTS.md` (`HealthCheck.id`'s doc comment names both checks but not their thresholds), `docs/LLAMACPP.md` (scoped to llama.cpp flags and endpoints, not NVIDIA driver/CUDA versioning) and `PLAN.md` §2.2 (explains *why* CUDA 13 matters — an architecture list the binary was not compiled for causes a silent CPU fallback — but not what driver a CUDA 13 build needs) were all checked directly; none states a minimum driver version. `cuda13_ok` uses the 580 floor directly (`PLAN.md` §2.2's own subject). `driver_ok` uses the 525 floor as this app's general viability floor — not published anywhere as *this app's* minimum, but grounded in `PLAN.md` §2.2's own framing: "Non-Blackwell NVIDIA prefers CUDA 13 and may fall back to CUDA 12", with nothing in this project's documents describing CUDA 11 or older as a supported fallback. ### F-007 — Recent llama.cpp releases are all `prerelease: true`, so the update client must include prerelease builds (T-020)

### F-008 — llama.cpp Windows CUDA asset names come in two schemes; the Releases list API caps at 1000 results; no release publishes per-asset checksums (T-020, subagent research)

Confirmed by a live paging pass over `ggml-org/llama.cpp` releases (1 Sept 2026, 108 releases checked, ~1077 `llama-b*bin-win-*` assets recorded verbatim to `C:/Users/Alieno/AppData/Local/Temp/t020-asset-research.json`):

- **Two CUDA naming schemes.** Current builds name the CUDA variant `bin-win-cuda-<major>.<minor>` (e.g. `llama-b10726-bin-win-cuda-13.3-x64.zip`). 2024–early-2025 builds named it `bin-win-cuda-cu<major>.<minor>` — a `cu` prefix *on the version* (e.g. `llama-b3066-bin-win-cuda-cu11.7.1-x64.zip`, `llama-b5559-bin-win-cuda-11.7-x64.zip`). Any asset-name parser (T-020's, and T-022's download/verify path) must accept **both** — T-020 does, taking the leading digit run as the major.
- **The Releases *list* API hard-caps at 1000 results.** `GET /releases?per_page=100&page=N` bottoms out around page 16 with HTTP 422 ("Only the first 1000 results are available"), so pure pagination cannot reach arbitrarily old releases. Per-tag calls (`GET /releases/tags/<tag>`) have no such cap — that's how the pre-2024 samples were fetched. T-020's "newest per backend" needs only the most recent page, so the cap is not a problem for this task, but any future task that walks full release history must know it.
- **No per-asset checksums are published.** Across all 108 checked releases: zero assets whose name contains `sha`/`sum`/`checksum`, and zero release bodies containing "sha256". `AvailableRelease.sha256` is therefore always `None` from this source — the field exists for T-022's verification path, and nothing in the Releases API populates it today.

### F-009 — The `zip` crate's `extract()` sanitizes rather than rejects; `Path::is_absolute()` is `false` for POSIX-style paths on Windows (T-022)

The zip crate (2.4.2) `extract()`'s `safe_prepare_path` is `pub(crate)` and *relocates* absolute paths into the destination instead of refusing them — so delegating extraction to it would silently write `C:\evil.txt`-style entries inside the target. T-022's installer therefore validates every entry name itself (reject `..` components, absolute paths, drive letters, symlink entries; abort the whole extraction with `AppError::UnsafeArchiveEntry`), in a first pass over all entries before any write. Second pitfall: on Windows `Path::new("/foo").is_absolute()` is `false` (it is rooted at the current drive — which is exactly what makes it escape-capable), so the validator checks the raw leading byte (`/` or `\`) explicitly rather than trusting `is_absolute()`. The crate's own writer (`ZipWriter::start_file`) stores hostile names verbatim (no sanitization), which is how the malicious-fixture tests build real escape archives. The symlink-traversal CVE-2025-29787 was fixed in 2.3.0; 2.4.2 is out of range.

### F-003 — ESLint's core `no-undef` false-positives on TypeScript's ambient globals; `tsc`'s `@ts-expect-error` matches on comment text, not intent (T-005)

Two related gotchas hit while wiring T-005's type-level test and the app's screen-registry type.

**`no-undef` and the global `JSX` namespace.** `@types/react` declares `namespace JSX` both under `React.JSX` and, separately, globally via `declare global { namespace JSX {...} } ` (deprecated but present, and what `tsc` itself resolves). ESLint's core `no-undef` rule doesn't read ambient `.d.ts` global declarations, so referencing the bare `JSX` type (e.g. `Record<RouteId, () => JSX.Element>` in `src/App.tsx`) passes `tsc` but fails `eslint`'s `no-undef` with `'JSX' is not defined`. This is a known class of false positive — typescript-eslint's own docs recommend disabling `no-undef` for TypeScript files, since the type checker already covers it more accurately. Fixed by adding `"no-undef": "off"` to `eslint.config.js`'s `**/*.{ts,tsx}` rules block, with a citation to typescript-eslint's troubleshooting page. Not scoped to `src/`-only files or to T-005 — the false positive applies to any ambient global type, so the fix is general.

**`@ts-expect-error` is matched structurally, not semantically.** `tsc` treats *any* single-line comment whose text begins with `@ts-expect-error` (immediately after `//`) as a real suppression directive for the following line — including one that appears inside an explanatory paragraph of prose, with no intent to suppress anything. `src/components/ui/loading.test.tsx`'s original draft explained the type-level-test pattern in a comment block that included the sentence "`@ts-expect-error` only needs to be *seen* by tsc, not executed" — and because that sentence started its own comment line, `tsc` parsed *that* line as the real directive, found no error on the following line (another comment), and failed the build with `Unused '@ts-expect-error' directive`, while the actual test fixture two lines later went unchecked. Fixed by rewording the prose so no explanatory line begins with the literal token sequence. Worth knowing for any future type-level-test file: never start a comment line with `@ts-expect-error` unless that line is the real directive.

### F-001 — GitHub Actions pwsh steps propagate the last native exit code (T-000)

GitHub Actions appends `exit $LASTEXITCODE` after every pwsh `run:` block. A step that deliberately runs a command expected to fail (e.g. `cargo clippy` on broken code) **fails the step even after a successful `$LASTEXITCODE` check**, unless the script ends with an explicit `exit 0`. Caught in the T-000 demo job (run 30928203565): the "Expect clippy to fail" step printed "clippy failed as expected (exit 101)" and then failed with exit code 1. **T-025's `scripts/probe-router.ps1` steps must end each probe with an explicit exit code** when a command is expected to fail.

Also observed: `windows-latest` currently resolves to Windows Server 2025 (image `windows-2025-vs2026`, VS 2026 build tools preinstalled), and `actions/checkout@v4` triggers a Node-20 deprecation warning — it runs on Node 24.

### F-002 — ts-rs 12.x: a shared `export_to` target does not produce one clean file; per-type files plus a collector does (T-002)

`docs/adr/adr-001-type-generation.md` left this as T-002's open question. Reasoned from ts-rs's docs first, then **confirmed empirically**: a real `npm run generate-types` run (owner, real toolchain) produced all 39 per-type files and collected them into one `src/lib/types.ts` exactly as designed, no collisions, no missing types.

ts-rs's own docs (https://docs.rs/ts-rs/12.0.0/ts_rs/) say `#[ts(export)]` generates one `#[test]` fn per type, each writing that type's binding to disk when `cargo test` runs. Directing several types at the same `#[ts(export_to = "...")]` path means several independent test functions — run by `cargo test`'s own parallel test harness, order and concurrency unspecified — writing to the same file; nothing in ts-rs's documented behavior claims these writes merge or serialize against each other. The default (no `export_to` override) writes one file per type, named after the type, which has no such collision because no two types share a target path. **T-002 uses the default and collects afterward** (`scripts/generate-types.mjs`): `TS_RS_EXPORT_DIR` points at a scratch directory (`src-tauri/target/ts-rs-bindings/`, see D-007), and the script concatenates every `*.ts` file there into `src/lib/types.ts`, stripping the self-referential `import type { X } from "./Y"` lines ts-rs emits for cross-type references — meaningless once everything shares one file.

Also confirmed by the same run: `ts-rs` 12 without the `format` cargo feature emits unformatted, single-line-per-type output, matching the docs' own example — but *with* quoted object keys on every field (`{ "kind": "Cuda", major: number, }` — the tag key quoted, the rest not) and a trailing comma after every field, including nested inline objects; the first hand-transcribed version of this file got both wrong (unquoted tag keys, missing some trailing commas) and was replaced with the real captured output. Rust doc comments are carried over as JSDoc `/** ... */` blocks ahead of the field or type they document. `TS_RS_LARGE_INT` was left unset, so `u64`/`i64`/`u128`/`i128` fields map to TypeScript `bigint`, not `number`. `DateTime<Utc>` needs the `chrono-impl` cargo feature. **`serde_json::Value` (`ServerProps.raw`) does *not* work cleanly with the `serde-json-impl` feature**: it emits a bare `raw: JsonValue` reference with no `JsonValue` definition anywhere in the exported set — a dangling type the moment files are concatenated. Fixed with `#[ts(type = "unknown")]` on that one field instead, and the feature is no longer enabled. `PathBuf` and `IpAddr` need no extra feature — both are covered by ts-rs's default foreign-type impls, confirmed by the same run.

### F-011 — Router registration channel is `PresetDeclaresPath` (T-025, empirical probe)

Confirmed by running the b9196-cpu build in router mode against prepared fixtures.

- **Q1 (absolute paths):** `--models-preset` accepts absolute paths. A preset with `model = E:\LMM\fixtures\model-a.gguf` registered the model as `test-external`. Non-existent paths also register (lazy loading) — the model only fails when actually loaded for inference.
