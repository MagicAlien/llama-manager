# Development environment

Everything needed to work every task in `docs/TASKS.md`, from T-000 to T-065.

## What you do *not* need

Worth stating first, because it is unusual and it is deliberate.

- **No NVIDIA GPU.** GPU access goes through the `NvmlProvider` trait, and every task that touches it is tested against mocks (T-010, T-060, T-061). A machine with no GPU exercises a required code path rather than blocking work.
- **No CUDA toolkit.** The app downloads prebuilt llama.cpp binaries; it never compiles CUDA code.
- **No real model files required.** GGUF fixtures are synthetic and generated by `scripts/make-gguf-fixture.py`, including the 65 GB one. If you *do* have a real model on disk, point `LLAMA_MANAGER_REAL_GGUF` at it and an extra set of tests runs against it — see "Testing against a real model" below. Recommended if you can, but never required.

A developer laptop with no GPU can take every task to green.

## What you *do* need that you might not expect

**A CPU build of llama-server, for three tasks.** T-023 parses `llama-server.exe --help`; **T-025 runs it in router mode to observe how models actually register**; T-043 maps real stderr messages to diagnoses. Both need output that a real binary actually produced, and a hand-written fixture defeats the purpose of the test — it asserts the parser agrees with the person who wrote the fixture, which is the same person who wrote the parser.

The CPU build runs on any machine. **The agent downloads it itself** as part of T-023 and reuses it in T-025; it is not a prerequisite you install up front, and it is not committed. What gets committed is the captured text:

```powershell
# T-023 does this for at least three builds of different ages
.\llama-server.exe --help > src-tauri\fixtures\help\b9196-cpu.txt
```

For T-043, the failures reproducible without a GPU — port in use, missing model file, malformed flag, corrupt GGUF — are captured the same way. The GPU-dependent ones (missing CUDA DLL, VRAM exhaustion, driver mismatch) are hand-written from upstream error strings and **marked in the fixture file as unverified**, so the owner can replace them with real captures later. Never relabel a hand-written fixture as a capture.

## Required

### Windows 11 x64

The app is Windows-only and several behaviours are platform-specific: DPAPI, the process tree kill in T-040, junction creation in T-029, registry access for launch-at-startup in T-063, path handling throughout. Do not develop on Linux or macOS and expect the tests to be meaningful.

**NTFS is required** on whichever volume holds the repository, because the large fixture is a sparse file: 65 GB addressable, a few megabytes actually allocated. Junction creation (T-029) also requires NTFS.

**Sparseness is not automatic on Windows.** On ext4, seeking past end-of-file and writing creates a hole by itself. NTFS does not: extending a file without marking it sparse makes Windows zero-fill it for real, and you get 65 GB genuinely consumed. The file must be flagged sparse *before* being extended — `fsutil sparse setflag <path>`, or `DeviceIoControl` with `FSCTL_SET_SPARSE`. T-030 makes this an acceptance criterion, so a script that gets it wrong fails a test rather than filling your disk.

Check any fixture with:

```powershell
fsutil sparse queryflag src-tauri\fixtures\huge.gguf
Get-Item src-tauri\fixtures\huge.gguf | Select-Object Length, @{n='OnDisk';e={(fsutil file queryvaliddata $_.FullName)}}
```

Never copy a sparse fixture with a tool that does not preserve sparseness — it expands to full size. This is one reason generated fixtures are gitignored.

### Rust 1.88 or newer, MSVC toolchain

```powershell
winget install Rustlang.Rustup
rustup default stable-x86_64-pc-windows-msvc
rustup component add clippy rustfmt
rustc --version   # must be >= 1.88.0
```

1.88 is the MSRV of `ts-rs` 12.x (ADR-001). The **MSVC** target is required — the GNU toolchain is not supported by Tauri on Windows.

### Visual Studio Build Tools 2022

Rust's MSVC toolchain needs the Microsoft linker and the Windows SDK. Install the **Desktop development with C++** workload.

```powershell
winget install Microsoft.VisualStudio.2022.BuildTools
```

Then select that workload in the installer. Without it, `cargo build` fails with a `link.exe` error that does not obviously point at the cause.

### WebView2 runtime

Tauri renders through WebView2 (`PLAN.md` §2.5). It ships with Windows 11, so normally nothing to do — but confirm it is present before assuming a blank window is your bug:

```powershell
Get-ItemProperty "HKLM:\SOFTWARE\WOW6432Node\Microsoft\EdgeUpdate\Clients\{F3017226-FE2A-4295-8BDF-00C3A9A7E4C5}" -ErrorAction SilentlyContinue
```

If absent, install the Evergreen Runtime from Microsoft.

### Node.js LTS

```powershell
winget install OpenJS.NodeJS.LTS
node --version    # 20.x or 22.x
```

Use npm — the lockfile is `package-lock.json`. Do not introduce pnpm or yarn without an ADR; a second lockfile in the repository is a review rejection.

### Python 3.10+

Only for `scripts/make-gguf-fixture.py`. Not a runtime dependency and never shipped.

```powershell
winget install Python.Python.3.12
```

### Tauri CLI

Installed as a dev dependency by T-001's scaffold, so `npm run tauri` works after `npm install`. A global install is optional and not required by any task.

### A free port for the endpoint listener

From T-042 onwards the test suite binds a listener. Tests use ephemeral ports and clean up after themselves, but **if something on your machine already holds `8080`, the default configuration's happy-path tests will exercise the `BindFailed` branch instead** — which passes, and misleads. Check before blaming the code:

```powershell
Get-NetTCPConnection -LocalPort 8080 -ErrorAction SilentlyContinue
```

## Optional

- **NVIDIA driver** — only if the machine has an NVIDIA GPU and you want `NvmlProvider` to return real data instead of mocks. Never install a CUDA toolkit for this project.
- **A real GPU-enabled llama-server build** — only for the checks in `docs/owner-verification.md`.
- **VS Code** with `rust-analyzer` and the Tauri extension, or any editor with rust-analyzer.

## First run

```powershell
git clone <repo> && cd llama-manager
npm install
npm run tauri dev
```

Then, before opening any PR:

```powershell
cargo fmt --check
cargo clippy -- -D warnings
cargo test
npm run lint
npm run test
npm run generate-types   # must leave src/lib/types.ts unchanged
```

These are exactly the CI gates from T-000 and T-002. Running them locally first saves a round trip.

## Repository configuration to create in T-001

**`.cargo/config.toml`** — `ts-rs` needs an export directory so generated types land in `src/lib/` rather than the default `bindings/`:

```toml
[env]
TS_RS_EXPORT_DIR = { value = "../src/lib", relative = true }
```

**`rust-toolchain.toml`** — pins the toolchain so CI and every developer agree:

```toml
[toolchain]
channel = "1.88"
targets = ["x86_64-pc-windows-msvc"]
components = ["clippy", "rustfmt"]
```

**`.gitignore`** must exclude, at minimum: `target/`, `node_modules/`, `dist/`, `src-tauri/fixtures/*.gguf` (generated, and the large one is enormous when copied off a sparse-aware filesystem), and any downloaded llama-server binary or archive. Captured `--help` and stderr text under `src-tauri/fixtures/help/` and `src-tauri/fixtures/stderr/` **is** committed — it is small, and it is the whole point.

## Fixtures

Generated, never downloaded:

```powershell
python scripts/make-gguf-fixture.py --arch llama --quant Q4_K_M --layers 32 --out src-tauri/fixtures/small-llama.gguf
python scripts/make-gguf-fixture.py --arch qwen3 --quant NVFP4 --layers 64 --out src-tauri/fixtures/nvfp4.gguf
python scripts/make-gguf-fixture.py --arch deepseek2 --moe --experts 128 --layers 60 --out src-tauri/fixtures/moe.gguf
python scripts/make-gguf-fixture.py --arch llama --quant Q4_K_M --layers 80 --size 65GB --sparse --out src-tauri/fixtures/huge.gguf
```

The script itself is written in T-030. Until then it does not exist — that is expected, not a broken setup.

### Testing against a real model

Synthetic fixtures have one blind spot worth naming: the generator and the parser are both written from the same understanding of the GGUF format. If that understanding is wrong somewhere, both share the error and the tests pass anyway — the suite proves internal consistency, not correctness. The same reasoning is why T-023's `--help` fixtures are captures rather than hand-written.

A real model file breaks that circularity. If you have one on disk, of any size:

```powershell
$env:LLAMA_MANAGER_REAL_GGUF = "D:\models\some-model.gguf"
cargo test
```

Tests guarded by that variable parse the real file and assert that the extracted metadata is self-consistent and plausible. **When the variable is unset the tests are skipped with an explicit message** — never silently, and never as a failure. CI does not set it.

Point it at several models over time if you can, especially ones with different architectures, an MoE, and an NVFP4 quantization. Each one that parses correctly is evidence the synthetic fixtures are modelling the format faithfully; each one that does not is a bug the synthetic suite could never have found.

## Generated documentation

`docs/verified-flags.md` is **not** written by the running app. It is rendered from the database by a script and committed deliberately:

```powershell
npm run export-verified-flags     # wraps scripts/export-verified-flags.ps1
```

An application that writes into its own source tree is a bug. The database is the runtime source of truth (`runtimes.verified_flags_json`); the committed file exists so that `AGENTS.md` §1 has something to check against without running anything.

## CI

`windows-latest` on GitHub Actions ships Rust, Node and the MSVC build tools, so T-000's pipeline installs nothing beyond components and cached dependencies. If a task ever needs something not on that image, add it to the workflow **and** to this document in the same PR — a dependency that exists only in CI is a trap for the next developer.

CI does not download llama-server. T-023, T-025 and T-043 run against the committed captures and result files; the download happens once, on the machine working those tasks.
